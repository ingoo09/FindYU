## 1. 5시간 안에 시연할 세 흐름

지도·포인트·랭킹·운영 차트, 분석 자동 재처리 큐와 관리자 화면, 다단계 검색·후보마다 여러 각도 입력, 연락·실물 인계는 후속 범위다. 등록 장소와 습득 시각은 선택 입력이며 시연 데이터에는 둘 다 채운다. 이용자가 후보를 확인하고 최종 일치 여부를 판단한다.

## 2. AI 호출과 모델

**등록 분석과 사진·자연어 검색 모두 영남대학교 FactChat(BAZE) API Gateway로 Gemini를 호출한다.** 프론트와 Dashboard는 FindYU 백엔드만 호출한다. 로컬 검색 모델을 시작하거나 다운로드할 필요가 없도록 백엔드의 등록·검색·시작 경로를 전환한다.

| 환경 | 모델 표시명 | `model` 값 |
|---|---|---|
| 개발·테스트·통합 리허설 | Gemini 3.8 Flash | `gemini-3.8-flash` |
| 실사용 및 실사용 환경 리허설 | Gemini 4 Argon | `gemini-4-argon` |

- [FactChat 개발자 화면](https://factchat.yu.ac.kr/dashboard/developers)에서 개인 키를 관리한다. 호출 주소는 `https://factchat-cloud.mindlogic.ai/v1/gateway`이며, 모델 직접 호출은 `POST /chat/completions/`, 계정에 허용된 모델 조회는 `GET /models/`다. `Authorization: Bearer` 인증을 사용한다. [영남대 모델 목록](https://docs.mindlogic.ai/docs/ynu-ac/api-gateway/getting-started/models) · [인증](https://docs.mindlogic.ai/docs/ynu-ac/api-gateway/getting-started/authentication) · [Chat Completions](https://docs.mindlogic.ai/docs/ynu-ac/api-gateway/reference/chat-completions)
- 백엔드의 `BAZE_API_KEY`와 `FINDYU_BAZE_BASE_URL`, 공통 모델 설정 `FINDYU_BAZE_MODEL`을 재사용한다. 테스트에는 Flash를, 실사용 설정에는 Argon을 명시한다. 서버의 모델 설정으로 두 기능을 함께 전환하고 프롬프트와 응답 스키마는 공유한다. 등록과 검색의 프롬프트는 기능별로 관리한다.
- 공개 문서에는 두 ID가 모두 있다. 사용 계정의 권한, 이미지 입력 및 구조화 JSON 응답은 `GET /models/`와 소량의 호출로 확인한다. Argon 호출이 막히면 PM에게 해당 환경을 알리고 실사용 검증을 미완료로 기록한다. 모델을 자동 전환하지 않는다.
- 실제 호출은 허락받고 개인정보를 제거한 사진으로 한다. 키·원본 응답·사진 데이터는 브라우저, 로그, 커밋에 내보내지 않는다. 모델에 보내는 등록·검색 문장과 물품 속성은 사용자 데이터로 취급한다.

## 3. 등록과 촬영

| API 품목 | 기본 첫 사진 | 기본 두 번째 사진 |
|---|---|---|
| `스마트폰` | 후면 | 측면 버튼 쪽 |
| `이어폰` | 케이스 정면 | 이어버드를 케이스 옆에 놓거나 케이스를 연 모습. 구성품이 하나면 다른 각도 |
| `지갑` | 바깥면 | 카드·신분증을 빼고 펼친 면 |

UI에서 두 기본 사진이 있어야 분석·등록을 시작하고 추가 사진은 3장까지 받는다. 기본 첫 사진이 대표이며 기존 대표 변경 기능은 재사용할 수 있다. 대표는 `image`, 나머지는 `extra_images` 반복 필드다. API는 기존 1~5장 입력과 호환한다. AI 값은 기존 `check_form`·`needs_check`·`photo_hint`로 표시한다. 카드 번호·잠금화면의 개인정보·신분증 등은 보이지 않게 촬영한다.

사용자가 고른 품목과 수정값이 우선이다. 품목을 바꾸면 이전 품목의 AI 기종·브랜드·전용 속성을 UI와 저장에서 제외한다. `모르겠음`은 미입력이고, 이어폰 브랜드는 직접 고른다. 같은 사진 묶음에서만 `analysis_id`를 재사용한다. 명시적으로 직접 입력해 등록하는 경우는 `defer_analysis=true`(목표)를 보내고, 서버는 사진·입력값을 저장해 `registered`와 실제 `id`를 반환한다. 저장된 수동 건도 검색 후보가 된다. 이 분기에서는 등록 분석을 새로 호출하지 않는다. 현재 API에 상태를 추가하거나 큐를 구축할 필요가 없다.

## 4. 검색 입력·결과 계약

1. 백엔드는 `/search`의 사진 `image` 또는 설명 `description`을 받는다. 기존 품목·체크 폼 필터에 따라 다른 값은 제외하고, 미확인 값은 `filter_check`에 남긴다. 장소·습득/분실 시각은 비교 보조 정보다.
2. 검색 대상으로 저장된 습득물 중 게이트웨이 호출에 보낼 후보를 고른다. 5시간 MVP 기본값은 **요청당 최대 10건, 검색 사진 1장과 각 후보 대표 사진 최대 1장**이다. 후보가 10건을 넘으면 요청에 명시한 장소의 일치, 시각의 근접, `created_at`·`id` 최신순을 차례대로 써 결정적으로 좁힌다. 장소·시각 미입력 시 그 기준을 건너뛴다. 사진 검색은 읽을 수 있는 대표 이미지가 필요하고 설명 검색은 저장된 외형 정보도 비교에 쓸 수 있다. 선택 후보 수를 `evaluated_count`로 돌려줘 결과를 해석할 수 있게 한다.
3. Gemini 한 번에 비교할 후보 묶음과 검색 입력을 전달한다. 모델은 **입력 후보 숫자 ID의 순서와 관찰 가능한 짧은 근거**만 돌려준다. 백엔드는 중복·목록 밖 ID·형식을 검사하고, 검증된 ID를 실제 DB 레코드와 결합한다. 후보가 없으면 호출하지 않고 200과 `results: []`를 반환한다. 게이트웨이 또는 응답 형식 오류는 API 오류로 전달한다.
4. `results` 순서가 순위다. 결과는 앱의 `top_k=5` 이내다. `match_reasons: string[]`는 P0 추가 필드로 비어 있을 수 있다. 이전 숫자 유사도 필드를 화면이 요구하지 않도록 전환한다. 생성 점수를 퍼센트로 표시하지 않는다. 기존 필드를 남겨야 하는 소비자가 확인되면 합의한 전환 기간에 `null`로만 둔다.

| 화면 동작 | FindYU API | 연결할 필드 |
|---|---|---|
| 체크 폼 | `GET /form-schema` | `category_field`, `forms`, `unknown_option` |
| 분석 | `POST /items/analyze` | `image`, `extra_images` → `analysis_id`, `check_form`, `photo_hint` |
| 등록 | `POST /items` | `item_type=found`, 사진, `analysis_id` 또는 `defer_analysis`, `form_answers` JSON 문자열, 선택 `location`, `occurred_at`, `description` → 물품 `id` |
| 검색 | `POST /search` | `image` 또는 `description`, 선택 `category`, `filters` JSON 문자열, `location`, `occurred_at`, `top_k` → `results`, `total_candidates`, `evaluated_count` |
| Dashboard | `GET /items?item_type=found&sort=newest&page=1&page_size=20` | 선택 `category`, `location` → `items`, `total`, `page`, `total_pages`, `has_next` |
| 장소·상세 | `GET /items/locations?item_type=found`, `GET /items/{id}` | `locations[].location`, 상세 물품 객체 |

브라우저의 `/api`는 Vite 프록시가 제거한다. 화면은 `id`, `image_url`, `images[].position`, `form_values`, `description`, `location`, `occurred_at`(습득 시각), `created_at`(등록 시각)을 기존 타입으로 읽는다. `occurred_at` 입력은 기존 캠퍼스 현지 `datetime-local` 규칙을 따르고, 서버 순서는 그대로 쓴다. 검색 0건과 오류는 구분한다. 기존 형식의 `detail`도 화면에서 처리한다.

```json
{
  "results": [{"id": 12, "category": "이어폰", "match_reasons": ["흰색 충전 케이스 형태가 유사함"], "filter_check": {"has_cover": "미확인"}}],
  "total_found_items": 3,
  "total_candidates": 2,
  "evaluated_count": 2
}
```

위 JSON은 부분 응답 mock이다. 신규 전송 필드는 백엔드가 `docs/API.md`와 같은 커밋에서 확정한다. 코드·API 우선순위는 저장소 `AGENTS.md`, `CLAUDE.md`, 최신 `docs/API.md`를 따른다. 공통 규칙이나 이전 API 문서에 과거 모델 경로가 남아 있으면 PM과 백엔드가 각자 소유 문서를 갱신한다.
